## Original Request (condensed)

Master prompt (user paste, 2026-11-17): "Eliminate DoS Risks in Database Health Checks" — implement the fixes for the three weaknesses identified by this session's security audit of `/health`:

- **Problem A** — uncancelled database queries can permanently exhaust the connection pool (network black hole on an established connection keeps a checked-out client forever; the 3 s `Promise.race` bounds only the caller).
- **Problem B** — every health-check request can initiate a new database probe (endpoints exempt from throttler/memory-protection guards by design; no single-flight, cache, or concurrency limit).
- **Problem C** — pool capacity depends on the implicit pg-pool default of 10.

Mandatory two-phase workflow: read-only investigation + proposal first, explicit approval before implementation; no commits unless requested. The Phase 1 proposal was produced in plan mode and approved by the developer (with three decisions: pool capacity via env var; runtime `statement_timeout` 30 s with CLI migrations off; Toxiproxy added to the db-tier tests). Full original text preserved in the session history.

## Investigation Findings (Phase 1, source-verified)

All verified against the installed sources, not documentation — three common assumptions refuted:

1. pg 8.23.1 `query_timeout` does **not** destroy the connection in default (non-pipeline) mode; it rejects only the query promise (`client.js:702-737`) — useless against a black hole.
2. Kysely 0.29.8 releases checked-out clients cleanly, never with an error (`release(Boolean(discarded))`); a hung query keeps its client checked out indefinitely.
3. MikroORM 7.2.9's abort options (`signal` + `inflightQueryAbortStrategy`) cancel through a separate control connection — itself black-holed in the attack scenario — and defer the pool release until the hung query settles.

The only deterministic reclaim path is a local socket close: pg's public `client.end()` force-disconnects hung queries ("a hung query could block end forever — force disconnect", `client.js:822-824`), the connection `'end'` handler rejects all pending queries (`client.js:203-207`), and `client.release(err)` makes pg-pool evict the client (`pg-pool/index.js:392-397`).

3. **CR-03 (Low)** — unguarded partial-startup teardown in the db-spec masked root errors. Fixed: guarded teardown steps.

## Remaining Limitations (documented in ADR-036)

- Application (non-probe) clients under a true black hole still hang until the OS TCP retransmission timeout (~15–30 min) or until the server-side 30 s `statement_timeout` aborts the statement when the server is reachable; client-side forced eviction of hung application queries is deliberately out of scope.
- TCP keepalive detects dead peers on idle connections only (OS-dependent); it cannot detect black-holed in-flight queries.
- Pool exhaustion reports through health as "database unavailable" (degraded/503) — a deliberate readiness-gating conflation.
- The black-hole test is container-network fault injection (Toxiproxy timeout toxics), not a real NIC-level fault; it reproduces the silent-drop semantics the attack relies on.
